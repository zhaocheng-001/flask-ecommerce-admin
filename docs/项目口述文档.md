# Flask 百战电商后台 - 项目口述文档

> 用于面试讲解 / 答辩汇报，按「项目是什么 → 怎么做的 → 亮点在哪 → 遇到什么问题」四段展开，全程约 3-5 分钟。

---

## 一、一句话介绍项目

这是一个基于 Flask 的电商后台管理系统，提供用户认证、商品管理、订单管理三大模块，采用「接口层 api → 服务层 service → 模型层 model」三层架构，热门商品列表引入 Redis 缓存，全部接口统一 JSON 返回体，并用 Postman 完成了全量接口测试。

## 二、技术选型与理由

- **Flask 而不是 Django**：电商后台接口数量可控，Flask 轻量灵活，通过蓝图（Blueprint）按模块拆分路由，规模大时也不会失控。
- **SQLAlchemy + MySQL**：ORM 屏蔽了手写 SQL 的重复劳动，模型即表结构，代码即文档。
- **Redis**：热门商品是典型的高频读、低实时性要求场景，用 Redis 缓存 60 秒能显著降低数据库压力。
- **Session 而不是 JWT**：这是后台管理系统，前后端同域或携带 Cookie 即可，session 服务端可控、可随时踢人，实现也最简单。

## 三、功能模块讲解

### 1. 用户认证与权限

- 密码用 werkzeug 的 `generate_password_hash`（pbkdf2:sha256 算法加盐哈希）加密入库，数据库中**永远不存明文**，校验用 `check_password_hash`。
- 登录成功后把 `user_id`、`role` 写入 Flask session；`before_request` 钩子把 session 信息注入 Flask 的 `g` 对象，接口里直接用 `g.user_id` 取当前用户。
- 权限用两个装饰器实现：`login_required` 拦截未登录，`admin_required` 拦截非管理员，商品的新增/修改/删除和订单状态流转只有管理员能操作，返回 403。

### 2. 商品模块

- 接口覆盖：分页列表（支持名称关键字、分类筛选）、详情、新增、修改、删除。
- 商品表设计要点：`price` 用 `DECIMAL(10,2)` 避免 float 精度丢失；`sales` 累计销量字段加索引，作为热门排序依据；`status` 控制上下架。

### 3. 订单模块

- 创建订单流程：校验明细 → 逐个查商品校验上架和库存 → **扣库存 + 写订单主表 + 写明细表在同一个事务里提交**，任何一步失败整体回滚，不会出现"库存扣了订单没生成"的问题。
- 明细表存的是下单时的商品名称和价格**快照**，商品以后改价不影响历史订单金额。
- 订单状态机：0 待支付 → 1 已支付 → 2 已发货 → 3 已完成，另有 4 已取消，状态流转由管理员接口控制。

### 4. Redis 缓存热门商品

- 缓存策略：按销量倒序取前 N 条，key 为 `hot_products:{top}`，TTL 60 秒，先读缓存、未命中查库后回填。
- **降级设计（亮点）**：Redis 连接失败时捕获异常、自动降级直查 MySQL，服务不报错、接口永远可用；返回体里的 `from_cache` 字段可以直观验证缓存命中情况，Postman 里连续请求两次就能看到第二次 `from_cache=true`。

## 四、工程质量

- **统一返回体**：所有接口返回 `{code, msg, data}`，`code=0` 成功、非 0 失败，前端只需判断一个字段。
- **统一异常捕获**：业务代码里只管 `raise ApiError("提示信息")`，由全局 errorhandler 统一兜底转 JSON；404、405、500 也全部接管，不会向前端暴露 Python 堆栈。
- **配置与代码分离**：MySQL 密码、Redis 地址、SECRET_KEY 都支持环境变量覆盖，方便部署和切换环境。
- **Postman 全量测试**：`postman/` 目录下的集合覆盖全部 13 个接口，按"登录 → 商品 → 订单"的顺序即可完整走通。

## 五、可能被追问的问题（Q&A 预案）

**Q：Redis 挂了怎么办？**
A：`socket_connect_timeout` 设成 1 秒快速失败，捕获异常后降级直查 MySQL，同时返回体 `from_cache=false`，运维可以从监控上发现缓存失效，但用户侧无感知。

**Q：缓存和数据库不一致怎么处理？**
A：TTL 只有 60 秒，属于短周期最终一致；商品修改时也可以顺手删除对应缓存 key（主动失效），成本很低。

**Q：订单并发下单库存超卖怎么办？**
A：当前扣库存是 ORM 的 UPDATE，MySQL InnoDB 行锁在单条 UPDATE 场景下是安全的；更严格可以用 `UPDATE products SET stock = stock - n WHERE id = ? AND stock >= n` 的乐观方式，或者引入分布式锁，这是下一步优化方向。

**Q：为什么用 session 不用 JWT？**
A：后台管理系统安全性优先，session 服务端可随时作废；JWT 适合无状态的前后端分离/多端场景，两者可以并存，后续扩展移动端时再加 JWT 登录接口即可。
